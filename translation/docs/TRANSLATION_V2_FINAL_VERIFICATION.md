## 1. فحوص السلامة النهائية

### A. التحقق من المصطلحات (`7a7bc0b`)

**ما وجدته في الكود:**
- `reject_statuses` الافتراضي كان `("approved", "auto_verified")`.
- يعني أن اتفاق درسين على ترجمة واحدة كان كافيًا لرفض الترجمات الأخرى.
- اتفاق النموذج مع نفسه في درسين لا يثبت أن الترجمة صحيحة.

**الإصلاح:**

| الحالة | السلوك الآن |
|---|---|
| `proposed` | اقتراح في البرومبت فقط. يُسجَّل غيابه ولا يرفض |
| `auto_verified` | **تفضيل قوي:** يُعطى للبرومبتات كمصطلح الكورس، ويُسجَّل غيابه. **لا يرفض** إلا إذا أُضيف صراحةً إلى `reject_statuses` (بعد قياس موثوقيته في Phase 1) |
| `conflicting` | يُسجَّل التعارض، ولا تُفرض أي ترجمة |
| `approved` | قرار إنسان (اختياري). الوحيد الذي يرفض افتراضيًا |
| `rejected` | قرار إنسان (اختياري). **جديد:** المقابل المرفوض يُحذف من اقتراحات الوكيل في الدروس اللاحقة |

- التشغيل يبقى آليًا بالكامل، ولا شيء يحتاج مراجعة بشرية.
- **حدّ معروف:** «ضمن السياق المناسب» ما زال على مستوى المصطلح كله، لا على مستوى معنى المصطلح في سياق معيّن. التمييز بين معاني المصطلح مخطط في Phase 1.

### B. ردود الـ API والكاش (`7a7bc0b`)

**ما وجدته في الكود:**
- `chat_json` كان يرجّع `None` عندما لا يعطي النموذج JSON صالحًا.
- كل الأدوار كانت تحوّل `None` إلى `{}` ثم تخزّنه كنتيجة دائمة:
  - وكيل المصطلحات: قاموس فارغ «ناجح».
  - مولّد Gemini: نتيجة `empty`.
  - التصحيح والترتيب والتحرير: «لا نص».
- غياب مفتاح API كان يُخزَّن كخطأ دائم لكل وحدة.
- الخطأ الدائم كان يُكتب في مسار النتيجة نفسه.

**أنواع الفشل الآن:**

| النوع | مثال | ماذا يحدث | يُخزَّن كنتيجة؟ |
|---|---|---|---|
| فشل مؤقت | 503، 5xx، timeout، 429 للدقيقة | يُعاد بعد انتظار (حتى 5 محاولات)، ثم تتأجل الوحدة. بعد 3 وحدات فاشلة متتالية يتوقف المولّد في هذا التشغيل | لا |
| نفاد الحصة | حد يومي (`PerDay`) | يتوقف الدور، والوحدات الباقية تتأجل | لا |
| سقف الطلبات | `CallLimitReached`، سقف واحد لكل أدوار التشغيل | مثل نفاد الحصة | لا |
| فشل المصادقة | مفتاح ناقص أو غير صالح (401/403) | يتوقف الدور فورًا، وتتأجل الوحدات | لا |
| رفض دائم | 400، محتوى محظور | يُسجَّل في سجل الفشل، ويُحجب بعد محاولة واحدة | لا |
| JSON غير صالح | ردّ بلا كائن JSON | يُعاد مرتين داخل الطلب، ثم يُسجَّل في سجل الفشل. يُحجب بعد 3 تشغيلات (`max_unit_attempts`) | **لا** |
| نتيجة فارغة صالحة | JSON صالح بلا نص | `status = empty` | نعم، لأنها جواب حقيقي |
| نتيجة ناجحة | — | `status = ok` | نعم |

**الاستئناف الآمن:**
- كل فشل يُكتب في **سجل فشل** بجانب مسار النتيجة (`<unit>.failure.json`)، ولا يُكتب أبدًا في مسار النتيجة.
- يحتوي السجل: نوع الفشل، وعدد المحاولات، وتاريخها.
- إعادة التشغيل تكمل ما نقص فقط. النتائج السليمة لا تُعاد ولا تُحذف.
- **بعد إصلاح السبب** (مثلًا مفتاح أو برومبت):
  - الإعداد `models.retry_errors = true`، أو `start(..., retry_errors=True)`.
  - يعطي كل وحدة محجوبة محاولة إضافية واحدة.
  - عند النجاح تُكتب النتيجة، ويُعلَّم السجل `resolved_at`، ويبقى تاريخه.

**البنية التحتية مقابل الجودة:**
- `status.infrastructure`:
  - `complete`، أو `degraded` مع أسبابه.
  - أسباب `degraded`: دور متوقف، أو وحدات مؤجلة أو مرفوضة أو محجوبة، أو JSON غير صالح، أو كاش قديم، أو قاموس لم يُبنَ.
- `status.quality`: كم جملة نجحت في بوابة الجودة، وكم فشلت.
- **التشغيل المكتمل الذي فشلت بعض جمله في البوابة ليس `degraded`**، ويبقى في التقييم.

### C. سلامة المصدر والتوقيت (`f6eea51`)

**ما كان موجودًا من Phase 0:**
- كل وحدة في المخرج تحمل `source_units`، وفيها لكل وحدة أصلية: المعرّف، والنص، والبداية، والنهاية، ومحاذاة الكلمات.
- الوحدة المدموجة تحمل `merged_from`، و`start` و`end` من أول وآخر وحدة أصلية.

**ما أُضيف:**
- **`check_coverage`** يعمل قبل كتابة `translation_final.json`، ويوقف التشغيل إذا:
  - ظهرت وحدة أصلية أكثر من مرة، أو غابت، أو أُضيفت وحدة ليست في المصدر.
  - تغيّر ترتيب الوحدات.
  - تغيّر نص أو توقيت أو محاذاة كلمات.
  - اختلفت `start` و`end` للوحدة المدموجة عن أجزائها.
- **`source_readiness`** في المخرج وفي الـ manifest:
  - `translation_test`.
  - `audio_sync`: صحيح فقط إذا كان لكل وحدة بداية ونهاية.
  - `word_alignment`.
  - قائمة الوحدات الناقصة.
- التوقيت المفقود يبقى `null` ويُسجَّل، **ولا يُخترع**.
