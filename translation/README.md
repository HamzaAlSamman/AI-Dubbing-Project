# خطوة الترجمة للدبلجة (EN → AR) — الإصدار 1

خطوة ترجمة جاهزة للدمج في خط الدبلجة. المدخل: وحدات الترجمة (نص إنكليزي + سياق + توقيت).
المخرج: `translation_final.json`، وفيه لكل وحدة النص العربي المكتوب، والنص الذي يُقرأ بصوت TTS،
والمدة المتوقعة، وحالة القبول، وسبب أي رفض.

## الفكرة باختصار

لكل وحدة:

1. **توليد عدة ترجمات من مولّدات متكاملة:**
   - **HY-MT1.5-7B** (نموذج ترجمة متخصص، قالب بلا سياق): أعلى جودة في تجاربنا.
   - **LLM بطول مستهدف** (Gemini Flash Lite): نعطيه نطاق عدد الحروف العربية المحسوب من مدة المقطع وسرعة الصوت،
     ويرجّع نسختين، `fit` و`short`.
2. **التنظيف:** حذف علامات الكود والاقتباس حول المتغيرات، وحذف الافتتاح المكرر "إذًا، إذا".
3. **البوابة:**
   - **صلاحية النص:** عربي، وطوله معقول بالنسبة للوحدة.
   - **الجودة:** MetricX-24 QE ≤ 5.
   - **الإملاء:** hunspell-ar ≤ 5%. الكلمة التقنية التي يختارها مولّدان من عائلتين مختلفتين تُقبل تلقائيًا.
   - **الأرقام والنفي:** محفوظة كما في الأصل.
   - **المدة:** تُحسب على الشكل المنطوق (x تُنطق "إكس")، ويجب أن تتسع لها **نافذة الوحدة الحقيقية** على الخط الزمني:
     المقطع، ثم الصمت قبل الوحدة التالية ناقص 0.10 ث، ثم بداية مبكرة حتى 0.50 ث. ويُسمح بتسريع حتى 1.25×.
4. **حلقة تصحيح محروسة:** تعمل فقط للوحدات التي لم تنجح فيها أي ترجمة. يحصل المحرر على أفضل مسودتين مع مشاكلهما،
   ويُقبل تعديله فقط إذا نجح في البوابة كاملة. وإذا كانت المشكلة طولًا فقط، يجب ألا تسوء الجودة بأكثر من 0.5 MetricX.
5. **الاختيار:** أقل MetricX بين الترجمات المقبولة. إذا لم تُقبل أي ترجمة، تُعلَّم الوحدة `needs_review` مع السبب.

## الأساس البحثي

| المصدر | ما أخذناه |
|---|---|
| Lakew et al., *Isometric MT* (2021/22) | الطول جزء من المهمة. توليد عدة ترجمات ثم إعادة ترتيبها حسب الطول والجودة هو الحل المعتاد |
| *Prompting LLMs: Length Control for Isometric MT* (2025) | تحديد الطول صراحةً في الـ prompt. عدة ترجمات + فلتر طول + ترتيب حسب QE أعطت أفضل توازن (طول مناسب في حوالي 65–72% من الحالات) |
| *Length-Aware Speech Translation for Video Dubbing* (Interspeech 2025) | نسخ قصيرة/عادية/طويلة من نفس الترجمة، واختيار الأنسب بمدة متوقعة دون توليد صوت. التزامن تحسّن 16–20% |
| *Duration-based Translation with LLMs* (EMNLP 2025 demo) | تحويل مدة المقطع إلى هدف طول للنموذج، ثم تعديل متكرر |

لم نجد عملًا منشورًا على الدبلجة الآلية من الإنكليزية إلى العربية الفصحى مع ضبط المدة. هذه إضافة المشروع.

## التشغيل

```bash
python -m unittest discover -s translation/tests -v        # اختبارات بلا نماذج ولا إنترنت
cd translation
python -m dubbing_translation run --tasks <tasks.json> --master <master_source_only.json> \
       --work-dir <Drive>/.../translation_step [--replay NAME=FOLDER] [--label note]
python -m dubbing_translation runs --work-dir <Drive>/.../translation_step   # مقارنة التشغيلات
```

على Colab: المتغير `GEMINI_API_KEY` يُحمَّل من خلية الأسرار (17.0) **يدويًا**، لأن الأسرار لا تُقرأ من خلايا تشغّلها أداة آلية.

## تتبّع التجارب (MLOps)

- **الإعدادات:** `configs/translation_v1.toml`. كل قيمة تُنسخ إلى `manifest.json` وتدخل في بصمة `config_sha256`.
- **كاش للترجمات والدرجات** على Drive يُكتب مرة واحدة ولا يُستبدل:
  - المسار يتضمّن اسم المولّد ونسخة الـ prompt، فتغيير الـ prompt لا يخلط النتائج القديمة بالجديدة.
  - التشغيل يكمل من حيث توقف بعد انقطاع أو بعد انتهاء الحصة اليومية.
- **كل تشغيل له مجلد** `runs/<run_id>/` فيه:
  - `manifest.json`: الإعدادات، والـ git commit، والنماذج، وبصمة البيانات.
  - `translation_final.json`
  - `candidates_scored.csv`: كل ترجمة مرشحة مع كل قياساتها.
  - `metrics.json`
  - `refine_log.json`
- **`registry.jsonl`:** سطر لكل تشغيل، للمقارنة بين التشغيلات. نسخة MLflow اختيارية (`tracking.mlflow = true`).

## حدود معروفة

- العتبات (MetricX ≤ 5، والإملاء ≤ 5%) تقديرية وغير معايرة على أحكام بشرية.
- تقدير المدة خطؤه الوسيط حوالي 11%. يجب إعادة قياس سرعة الصوت عند تغيير الصوت باستخدام `timing.calibrate_rate`.
- الوحدات القصيرة جدًا (أقل من ثانيتين) قد تحتاج دمجًا مع الوحدة المجاورة، وهذا قرار مرحلة بناء الوحدات.
  هنا تُعلَّم فقط بـ `tiny_slot_consider_merging_with_neighbour`.
- لا ترفع إلى هذا المستودع العام أي نصوص محاضرات أو مخرجات أو مفاتيح. كل البيانات تبقى على Drive.
